# 累積經驗

本檔為特有之累積經驗,留給後續之嘗試、執行與判斷,由agent自行編列、擴充與維護.

## 一、同型錯誤：修了被指出的那個，沒回頭比對兄弟

本專案最反覆的失敗形狀。**已發生十八次**，其中第五次發生在補救第四次時、第六次發生在分析同型錯誤時、
第十、十一、十六次發生在**撰寫與維護用來防止第六次的工具時**，第十二次發生在一個**已被標記為「已修」的安全缺陷**上，
第十五次發生在**修那個安全缺陷的當下**（修補本身又留一個同型的洞），
第十七次發生在**新增擴充點（fetch 掛點）的當下**，且是由安裝方的 agent 在真實佇列上撞到、寫成提案才發現，本專案派出的雙複審當輪沒抓到；
第十八次發生在**修第十七次的當下**——新寫的唯一擁有者函數用「可自報的 reason」反推出口，而出口早已在手上；同一輪放寬網址比對時，沒回頭列以 ar-／vi- 開頭的**語系段**（它就在自己註解的已測語系清單裡）。這一輪雙複審抓到了。

**第 14、15、16 次是同一輪內連續發生的，且都由我自己造成**——那一輪我正在修複審指出的缺陷。
共同點：**我驗了「機制對不對」，沒驗「我餵給機制的那個值對不對」**。
第 14 次驗了閘門會不會略過，沒驗 1822 這個數字；第 15 次驗了判準擋不擋得住，
沒驗真實輸入長什麼樣；第 16 次驗了自檢會不會執行，沒驗它認不認得出本專案的書寫形態。
**可執行的判準：每加一個判準，先把「production 實際餵進來的值」印出來看一眼，不要用自己構造的值。**

**第 12 次最值得警惕**：`sgud/exp/experience.md` 三之表把 SSRF 列為「已發現並修正」，
於是它在後續每一輪都被跳過。**「已修」這個標記本身會讓一條缺陷免於再被檢視**——
而當初修的只是複審給的那個具體輸入。帳本記「已修」時要寫清楚**修的是哪一個成員、

**第 6 次特別值得記**：連「列舉軸的成員」這個動作本身都會犯——grep 範圍不夠廣就下「沒有」的結論（全域 §4 規則 1）。

**第 7 次的教訓不是「又犯了」，是「記下來不等於修好」**：它在上一輪就已經被寫進本表，
標明「未一併查」，然後就這樣擱著。帳本記錄的是**已知缺陷**，不是**已修缺陷**；
下一輪讀到本表時，每一列都要先確認它現在的狀態，不能因為「有記錄」就當作處理過了。

**第 8、9 次是同一個子形狀的第二、三例**：「curl 有的、playwright 沒有」。
UA／Referer／Accept-Language 是第一例。這個子形狀有明確的可執行判準——
**凡屬「四個抓取器都該做的事」，判準一律放共用模組，不寫在任一抓取器內**
（`requestIdentity.mjs`、`httpStatus.mjs` 即為此而生）。新增任何抓取器層行為時，
先問這句話，比事後逐一比對便宜。

**第 10 次最值得記**：防範措施本身也是「一個成員」，它一樣會漏列。
工具不會因為它的用途是防漏而自動免疫；**盤點腳本的掃描範圍本身就是一個需要被盤點的清單**，
故該腳本的 `SOURCES` 內留了一句話：新增存放站台知識的檔案時須同時登記。

### 有效的防範（依本專案實證）

1. **預設安全、例外標記**：讓「忘記」的後果偏保守。
   例：內容量閘門改為預設套用、只有標 `strength:'strong'` 者例外——忘記標的後果是多擋，不是誤放。
   但**「安全側」是相對於誰而言要想清楚**，見本檔七。
2. **加欄位前先問「這個欄位分的是哪個軸」**：第 5 次錯誤就是軸選錯。
3. **下「沒有 X」的結論前，先寫出 grep 的範圍**：第 6 次錯誤靠這一步就能避免。
4. **一個階段有幾個失敗出口，每個出口都要問同一個函數**：去留、紀錄該帶哪些欄位，這類「每個出口都要做的事」只能有一個擁有者；
   出口各自手寫尾段，必有一處漏（第 17 次）。判準：迴圈裡出現第二個 `continue`／`return finalize` 的尾段時，先把尾段收成一處再加分支。

## 二、驗證的三條實證教訓

### 1. 拿真實頁面，不要只用構造的 fixture

gelonghui 解析器有一條缺陷被標記「無法取得真實 gelonghui 頁面驗證其 state 結構」而擱置多輪。
**實際去抓就通了**（第一次 curl 逾時，第二次成功）。而且真實頁面同時證明兩件事：

- 觸發條件（`content` 為物件首個鍵）在真實頁面不成立——真實首鍵是 `id`
- **原定修法會直接讓真實頁面解析失敗**——真實 state 含 `tag:{name,color}` 巢狀物件，
  用「中間不得含大括號」收緊 regex 會找不到 content

正解是換方法（大括號配對切出物件範圍），不是調 regex 鬆緊。

**更該記的**：那句「無法取得」是**前一輪的自己**寫的，這一輪的自己把它當事實繼承，
還拿它當「等業主裁示」的理由。全域 §2.1 第 5 條「既有碼不是規格」——自己上一輪寫的註解也算，
而且更危險，因為讀到時會有「這我查過了」的錯覺。

### 2. fixture 要照真實頁面寫，不可照實作寫

`htmlChallenge` 曾寫成 `<title>Just a moment</title>`（無刪節號）。
真實 Cloudflare 頁是 `Just a moment...`。於是判識器改用全等比對而漏判**所有真實頁面**時，測試依然全綠。

判準：寫 fixture 時問「這個形狀是從真實頁面來的，還是從實作反推的？」

### 3. 假 server 能過不代表真實可行

camofox 的並發限制用假 server 測不出來——真實情境是兩個**真** server 搶同一個埠，
而假 server 測試裡只有一個假 server 在跑。

判準：凡以 fake 驅動的測試，都要問「真實情境的哪一部分被 fake 掉了」。

## 三、在做事的過程中掉出來的缺陷（讀碼看不出來的）

本專案數個真缺陷不是靠審查程式碼發現，而是靠**列舉輸入空間**與**去拿真實資料**：

| 缺陷 | 怎麼發現的 |
|---|---|
| `timeoutMs: Infinity` 導致立即逾時（要求不逾時、得到 1ms 逾時後被 SIGTERM） | 為 `getOpt` 寫邊界測試而列舉 `Infinity` |
| UA／Referer／Accept-Language 在 playwright 兩階完全失效 | 建「四個抓取器 × opt」對稱表 |
| gelonghui 跨物件抓錯內文 | 去抓真實頁面驗證 |
| SSRF：`URL_PARAM_PATTERNS` 未錨定網域，可對 `169.254.169.254` 發請求 | 外部複審實測。**注意：當時只修掉一個變體**，主變體（用真正的 linkedin 轉址網址帶任意目標）在下一輪複審才被發現，見上表第 12 次 |

**共同點**：都不是「讀這段碼覺得怪」，而是「把輸入空間攤開後某一格是空的／某一格的值不對」。

## 四、外部複審的價值紀錄

本專案數輪皆派兩位獨立複審（`dispatch-claude`／`dispatch-codex`，opus/sol、effort max）。實證：

- **自審的表一定有洞**。每一輪複審都推翻了我自認完整的表，且推翻的都是**核心論證**而非細節：
  - 第三輪：「empty 對合成內容數學上不可能觸發」被一個反例推翻，連帶推翻整個方案
  - 第五輪：「沒有任何站台同時出現在兩處」因我 grep 範圍不夠而不成立
  - 第六輪：**兩位複審獨立收斂到同一個最重要發現，而那是我在同一輪剛寫下的程式碼**——
    `parse:false` 使 `adapter.inspect` 成為 no-op。我在寫它時完整推理過閘門語意、
    還寫了註解替它辯護，仍然漏了 `opt.parse` 這個軸。
    **教訓：剛寫完的程式碼是最不該跳過複審的，不是最不需要複審的**——
    寫的人腦中有完整的意圖，正因如此最容易把「我想的」當成「碼做的」。
- **第七輪：兩位獨立推翻的是我的「理由」，不是我的「結論」**。我對 C1a 的結論（否決）是對的，
  但理由完全錯：我寫「以網址為鍵會漏判」，而真正的後果是**誤判**，且會打壞現行主流程——
  msn 與 weixin 的路由**不換網址**，該站的空殼與真文章網址完全相同，網址在那裡零判別力，
  改以 host 為鍵會讓那些站台永久抓不到。
  **對的結論配錯的理由，比錯的結論更危險**：它會通過檢查，然後在下一個決策點把錯的理由再用一次。
  兩位還一致指出**題目定義本身是錯的**——那三站的兩處知識本來就該分開，把正確的分工當缺陷去消滅。
  派工前我以為要審的是「哪個方案好」，實際最有價值的產出是「這個問題不存在」。
- **兩位的分歧本身是有用的資訊**。第六輪 A、B 對「camofox 該不該判識」給了相反結論。
  A 的事實面正確（`method:'curl'` 單階同樣無可升級卻照常判識，故現況不對稱），
  B 的成本面正確（末階誤判不可回復）。真正的解不在選邊，而在看出兩人各自只論證了一半：
  誤判不可回復，漏判也不可回復，**差別在誤判會出聲、漏判是靜默**。
  收到分歧時要找的是「他們共同漏掉的那個維度」，不是「誰比較有道理」。
- **兩位獨立複審會收斂到同一個最重要發現**，且各自找到對方沒找到的。單派一位會漏。
- **複審者的實測腳本要保留**（`tmp/probe*.mjs`），我逐條複跑過，屬實率高但**不可整批接受**：
  第五輪 A 主張「兩個掛點失敗處置不對稱必須收斂」，實測後發現差異有理由（parse 換抓取器
  會得到不同 html，fetch 完全不從網頁取），予以駁回。

- **第八輪：發現最重要缺陷的是安裝方的 agent，不是我派的複審**。內建 msn adapter 那一輪我派了雙複審審 fetch 掛點的設計，
  兩位都沒抓到 `fallback` 只在一個出口生效；安裝方在真實佇列（725 篇 msn）上用它時撞到，寫成提案。
  **使用端的提案是第三種複審**，價值在於它從真實用法而非從程式碼出發——複審者讀碼會順著我的註解走，使用者不會。
- **第九輪：兩位獨立收斂到同一個發現（去留函數以可自報的 reason 為鍵），且用的是不同方法**——A 以 20 個單點突變找出「拿掉也沒有測試會紅」的四處，
  B 以 4600 個情境對 HEAD 差分找出 248 格意外差異；B 另以真實網址抓到網址比對放寬過頭。兩者都是**我剛寫的碼**，且都在我自認完整的表之外：
  表沒有「reason 的來源」這個軸、沒有「語系段也以 ar-/vi- 開頭」這一列。突變測試是本專案第一次用來驗「表上的 ✔ 是不是真的有測」，值得留為常規手段。

## 六、與安裝方的關係（本套件的定位）

**套件的發版次數必然遠少於安裝方遇到新情況的次數。**

這句話是本套件多項設計決策的來源：站台會新增、會改版、反爬蟲手法會換；
若把這些寫死在套件裡，安裝方每遇到一次就得等發版。

具體推論：

- 站台知識、判識規則都應該是「套件給機制與預設、安裝方補自己遇到的」
- 內建清單是**預設值**，不是不可覆寫的規則
- 判斷新功能形狀時先問：**這是機制還是清單？** 清單一律要可覆寫

反例（本套件曾犯）：`routeByUrl` 的五組 PATTERNS 完全不可覆寫，
安裝方遇到新站台只能等發版；而同樣是站台知識的 `defaultAdapters` 卻可經 `opt.adapters` 覆寫——
同類知識兩種可覆寫性，本身就是不對稱。

### 「讓安裝方自己寫」與「做成內建預設」的分界（msn 一案）

msn 曾被判定為「安裝方自己寫 adapter」的範圍，安裝方也確實寫出來了。後來仍改為內建，理由不是
「套件應該包辦」，而是兩個**量得出來**的訊號同時成立：

1. **預設路徑的失敗是確定的，不是偶發的**。實測 12 篇真實文章，預設階梯三層全滅、每篇白耗 43 秒——
   任何沒寫 adapter 的安裝方都會一模一樣地踩到，這不是「某個安裝方遇到的特殊情況」。
2. **解法不含安裝方私有的東西**。內容 API 是公開端點、不需金鑰或登入；安裝方寫的與套件會寫的是同一份知識。

判準：**若解法需要安裝方私有的資源（金鑰、帳號、內部快取），留給安裝方；若任何人寫出來都是同一份，
且不寫就一定壞，那就是預設值，該內建。**「原則一：安裝方補自己遇到的」針對的是前者。

同一案順帶暴露的缺口：內建清單此前**無法停用或剔除**（只能逐站蓋過），上一輪複審就列過卻未處理，
內建由兩個增為三個時才補上 `useDefaultAdapters`。**內建清單每增加一個，停用它的能力就更重要一分**——
加內建之前先確認呼叫端拿得掉它。

內建 msn adapter 的 `fallback:false` 是量測後才定的：落回的存在理由是「還抓得到」，對 msn 量到的成功率是 0，理由不成立。
`inspect:false` 上一輪**沒標**，理由是「量到 0/12 被擋，沒有證據就不標」——這一輪改標了，而且是被安裝方的提案說服的。
教訓：**「量到 0/12 被擋」證明的是那 12 篇，不是「這類判識器該作用在此類內容上」**。內建判識器是對「爬回來的頁面」下的猜測；
API 組出來的 HTML 來源已知，那些猜測對它只剩誤判一個方向（圖多字少必判 `empty`、標題恰以 `access denied` 開頭必被擋，皆為靜態控制流可確定）。
量測回答「有沒有發生」，結構回答「會不會發生」；決定要不要豁免時兩個都要問，且後者不需要等前者。

## 七、「預設安全」要先問「對誰安全」——會靜默失效的擴充點

實作 `opt.detectors`（使用端註冊判識器）時，我把新欄位的預設值一律選在「安全側」：
`strength` 預設 `'weak'`，亦即受內容量閘門保護。理由當時說得通——與內建判識器一致，
忘記標的後果是少擋而非誤殺。

**接線完成後實測，註冊的判識器完全沒有反應**：

```
未註冊判識器: success ★挑戰頁被當文章 len=692
註冊判識器後: success | reason=undefined | message=undefined
```

原因是該機制的動機情境（長篇中文攔阻頁，可見文字 684 字）**依定義就在閘門之上**。
於是這個擴充點在它唯一存在理由的情境下必然無效——**機制看起來裝好了，實際是個 no-op**。

三點教訓：

1. **「安全側」是相對於某一方而言的**。對套件安全（不誤殺長文）＝對呼叫端無用（註冊了不生效）。
   選預設值時要問的不是「哪邊比較保守」，而是**「這個保護是為了防誰的錯誤？那個人是不是就是被保護對象？」**
   閘門防的是套件自己對全世界頁面所下的猜測；呼叫端的判識器不是套件的猜測，不歸它管。
2. **兩種失敗的可診斷性不對稱，這比「哪種比較常發生」更重要**。呼叫端寫太鬆 → 在他自己的關鍵字上
   出現可歸因的誤擋，查得出來；被閘門靜默跳過 → 「我註冊了但完全沒反應」，查不出來，
   且看起來就是套件壞掉。**寧可選會出聲的那種錯**。
3. **新擴充點必須用它的動機情境驗收，不是用構造的最小案例**。單獨呼叫 `inspectHtml` 的最小案例
   （短頁 + 關鍵字）當時是通過的；換成真正要解決的那類頁面才炸出來。
   這與本檔二之 1、2 同型：驗收樣本要來自真實動機，不可來自實作反推。

附帶記一筆同輪的小發現：`invalid-method` 的錯誤訊息列舉合法值時漏掉 `'auto'`——
而 `'auto'` 既合法又是預設值。它是由 `METHOD_OPTIONS` 之鍵產生的，而 `'auto'` 因為
「不對應單一階」被排除在該物件外。**值域被拆成兩層時，對外訊息容易只取到其中一層**。

### 這個形狀在同一輪內又出現了兩次

- **`adapter.inspect` 在 `parse:false` 時是 no-op**（外部複審實測）。我以 `opt.parse` 決定
  「要不要挑 adapter」，而 adapter 加上 `inspect` 掛點後，那個閘門的前提就消失了——
  `parse:false` 的呼叫端**用得到** adapter。後果不只是宣告失效：呼叫端白跑四階，
  最後只因末階 camofox 自身不判識而意外成功，回報的 `method` 還變成 `camofox`。
- **`fetch` 掛點若讓 `opt.method` 決定要不要跑，會是第三次**。複審 B 明確指出：
  註冊 fetch 又傳 `method:'curl'`（不想開瀏覽器，很常見）是高度共生的組合，
  跳過就等於「我註冊了但完全沒反應」。

**可執行的判準**（比「記得檢查」有用）：新增擴充點時，把套件內**每一個既有的旗標與閘門**
逐一列出來問「它會不會作用在這個新掛點上、作用了會不會讓它變成 no-op」。
本專案至今的答案是：內容量閘門會、`opt.parse` 會、`opt.method` 會、`opt.inspect` 會。
這份清單本身該進規則帳本，因為下一個掛點還要再問一次。

**更根本的一條**：這三次的共同結構是**我用一個既有的軸去閘一個新的軸**。
`opt.parse` 是「解析」軸，拿它去閘「挑選 adapter」；`opt.method` 是「爬法」軸，
想拿它去閘「要不要爬」。閘門的軸與被閘的軸必須是同一個，不是的話就是借來的權威。

## 八、改經 w-playwright 啟動之遷移（2026-11-13，排程第 442 項）

- **修前之測試不能「只是不跑真瀏覽器檔」就算安全**：修前之 `hasChrome` 本身就以真啟動探測（每檔一次），
  任何未以 `_fetchers` 替換抓取器之路徑也會真啟動。可靠作法是以 `NODE_OPTIONS=--import=<掛鉤>` 註冊
  ESM resolve 掛鉤，把**非 `node_modules` 內**之 `playwright`／`playwright-core` 匯入改指 stub（`launch` 一律拋錯並記錄堆疊）。
  mocha 平行之 worker 經 `NODE_OPTIONS` 繼承；以 `parentURL` 不含 `/node_modules/` 為條件，w-playwright 自身之相依不受影響。
  實測修前全套只擋到 4 次（皆為 `hasChrome` 之探測），證實其餘 40 檔不啟動瀏覽器——這是「下『沒有 X』前先確認範圍」之實證版本。
  同一掛鉤亦使修前紅測（接線測試對舊碼）可跑而不啟動瀏覽器：舊碼之 `chromium.launch` 落到 stub，替身呼叫 0 次 → 紅。
- **「降版」之前提要先查實裝**：設計以頂層 `node_modules/playwright-core` 為 1.65.0 判定本套件將由 1.65 降到 1.64.1；
  實查 `playwright@1.64.1` 帶巢狀 `playwright-core@1.64.1`，頂層 1.65.0 是 camofox 之相依，本套件之啟動從未用到。
  判斷「實際用哪一版」須沿匯入鏈找解析到的那一份，不看頂層。
- **被測函數每次呼叫自行啟動者，仍可每檔只啟動一次**：不必為測試加對外之注入選項（屬 API 變更）。
  w-playwright 之 `setBrowserTypeForTest` 替身收到合併後選項與 `next`：第一次呼叫 `next()` 真啟動，其後回同一行程之包裝
  （`newPage` 照真 `Browser.newPage(o)` 開新 context，`close` 只關本次之 context）。真 Chrome 之啟動由 5 檔約 28 次降為每檔至多 1 次；
  被取代之部分（行程只起一次、close 不關行程、首次失敗即沿用）須寫在 helper 內，讀測試結果時才知差異。
- **有頭檔會開可見視窗**：在有人使用之主機上跑全套須 `WFETCHWEB_SKIP_HEADED=1`；有頭之真啟動證據要另排（沙箱或經授權之時段）。
- **只管「會啟動」的 5 檔不夠（外審 terra 抓到三個洞）**：①auto 模式之測試在 curl 意外失敗時會升級到真瀏覽器階（含有頭），
  這些檔沒裝共用替身；②mocha 逾時不會取消進行中之抓取，`after` 還原替身後殘存之重試會走真路徑；③平行之各檔在不同行程，
  w-playwright 之登入守門只在同行程內序列化。對策：`test/tools/noBrowser.mjs` 於載入即裝「一律拒絕」之基底替身且永不還原
  （替身為堆疊，其餘替身疊在其上、還原後回到它），凡可達 `runPlaywright` 之測試檔皆匯入；`sharedChrome` 之真啟動以檔案鎖跨行程依序進行。
  教訓：安全不變式要以「預設拒絕、例外標記」實作（本專案原則三之 1），不要以「列舉會啟動者」實作——列舉漏一個就破。
- **`rg -L` 不是「不含者」**（是跟隨連結）；要列「不含某字串之檔」用 `rg --files-without-match`。盤點指令寫好後先以去掉匯入之副本驗證能抓到。

## 九、jsdom 30→31 升級之等價比對（2026-11-14，jd-fw2）

升級結論與數字見規則帳本四之 2026-11-14 列；此處記方法與教訓。

- **「修前」基線要重現鎖定之整棵樹，不是只裝舊版 jsdom**：`git archive HEAD package.json package-lock.json src test/tools` 解到 `./tmp`，

  本檔無替身（真 jsdom、真 Readability、真本機 HTTP 伺服器只計數）。該檔於 30.1.3＋HEAD 之 src 跑為 44 過 2 敗（`DISPLAY:NONE`＝31 之行為；接線）、
